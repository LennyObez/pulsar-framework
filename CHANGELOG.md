# Changelog

Format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).
Versioning follows [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added

- `FilePseudonymLookup`: a pseudonym mapping table that survives the process that wrote it. `InMemoryPseudonymLookup` was the only implementation the framework shipped, and its own attribute reads "Test/dev pseudonym lookup implementation" — a pseudonymisation service standing on it can mint a pseudonym and can never resolve or erase one after a restart, which defeats both the GDPR Art. 15 answer and the Art. 17 erasure `ForgetService` exists to perform. The new lookup rewrites the whole document under an exclusive lock rather than appending, because erasure is the control it serves and a tombstoned append-only file still holds the subject id it was asked to remove; a corrupt table throws rather than reading as empty, so an erasure is never reported against a table nobody could read. `SecurityWiring` now binds `PseudonymLookupInterface`, `PseudonymizationServiceInterface` and `ForgetServiceInterface` — all three classes had shipped since 1.0.0 and none was ever constructed outside its own test.
- `composer deploy:check` exists. Both env templates had documented that invocation since F19.4; composer answered "There are no commands defined in the \"deploy\" namespace" and exited 0. It now runs `php bin/pulsar deploy:check --env=production`.

- Native localized route slugs: translate URL path segments per locale (`/fr/developpement`, `/nl/ontwikkeling`) for a single route registered under a canonical key. Includes `SlugRegistry`, `LocalizedSlugMiddleware` (constant-time rewrite + configurable canonical 301 for non-canonical aliases, route parameters preserved), `LocalizedUrlGenerator` with the `route()` helper and `@route` directive, slug-aware hreflang/`x-default` output, and the `i18n:slugs:lint` console command (completeness + collision checks, wired into CI). Compiled once at boot with zero runtime cost when unconfigured.
- Managed Challenge: a self-hosted, privacy-preserving CAPTCHA provider (`captcha_provider: 'managed'`) — an invisible proof-of-work alternative to Cloudflare Turnstile / hCaptcha with no external service, no cookies, and no fingerprinting. Signed, single-use, expiring challenges (`sodium_crypto_auth`, master sub-key) solved in a Web Worker and verified server-side (signature → freshness → proof-of-work → replay cache). Ships `ManagedChallengeService`/`Verifier`/`Renderer`, the `@shield` directive, same-origin widget + worker assets (CSP `script-src 'self'` clean), and `managed_challenge_bits`/`ttl`/`field_name` config.
- i18n `negotiate_unprefixed_locale` config flag (default `true`, backward-compatible). When `false`, the active locale for an unprefixed URL is always the default locale instead of the Accept-Language–negotiated one, so default-locale URLs stay canonical and are never redirected to a negotiated localized-slug translation. The negotiated preference is exposed via the `_negotiated_locale` request attribute for application-level courtesy redirects at `/`.
- Turnkey locale preference: opt-in cookie-aware negotiation, courtesy redirect, and cookie persistence for the path-prefix locale strategy (all default OFF, backward-compatible). `locale_cookie_enabled` wires `CookieAwareLocaleNegotiator` (cookie + session outrank Accept-Language) and stamps a functional `pulsar_locale` cookie (`HttpOnly`, `SameSite=Lax`, `Secure` on HTTPS) on prefixed pages; `courtesy_redirect` 302s an unprefixed GET/HEAD to the visitor's locale prefix (the default locale stays canonical — no loop with the canonical 301); `courtesy_fallback_locale` sends visitors with no detectable language to e.g. `en` while keeping the default locale's `x-default` canonical. New config keys: `courtesy_redirect`, `courtesy_fallback_locale`, `locale_cookie_enabled`, `locale_cookie_name`. Centralizes logic each site previously re-implemented.
- `@shield` managed-challenge strings are localizable: the `<noscript>` fallback and the screen-reader status are resolved from the i18n `shield` translation domain (`noscript`/`verifying`/`complete`/`error`), falling back to built-in English. The widget announces the localized status through a visually-hidden `role="status"` live region.
- The framework's own schema now ships as migrations. Five new files under `src/<Module>/Database/Migration/` create the tables the framework itself requires — `saga_states` (`20260821000001`), `workflow_instances` and `workflow_transitions` (`20260821000002`), `failed_jobs` (`20260821000003`), `outbox_events` (`20260821000004`) and `saga_step_results` (`20260821000005`) — applied by `php bin/pulsar migrate:run` alongside your project's and each extension's (ADR-0043). Each step re-checks the state it would create before creating it, so applying the set to a host that already holds a table changes nothing, with one intended exception: `20260821000004` adds `outbox_events.dead_lettered_at` where it is absent and rebuilds the pending index that was compiled before that column existed — an upgrade that previously lived in a `migrateSchema()` method nothing ever called, so no deployment has ever received it. `saga_step_results` had no DDL in any form before this. "Changes nothing" includes the shape: a fresh install gets `LONGTEXT` payload columns and a `utf8mb4_bin` table collation on MySQL, and a table that already exists keeps the type and collation it has, with the migration recorded as applied either way. For the only one of the six a deployment can have adopted that is a no-op — `outbox_events` came from an installer that already wrote both — and [docs/upgrade.md](docs/upgrade.md#what-an-adopted-table-does-not-get-and-what-that-costs) covers the host whose table arrived some other way: what it keeps, what that costs on MySQL, and the `ALTER` that converges it.
- `down()` on a framework schema migration refuses rather than destroys. It counts the table's rows first and throws instead of dropping when the count is not zero: on a host that had the table before the migration, `up()` created nothing, so the `DROP` would not reverse a change — it would delete integration events committed but not yet published, untriaged dead-lettered jobs, or sagas with compensation still owed. `migrate:rollback` now prints the refusal as a `Caused by:` line (matching `migrate:run`, which already did); previously only the runner's `Migration <version> (down) failed` wrapper reached the operator, naming nothing about what would have been destroyed. Rolling back stops at the refusal and resumes where it stopped once the table is emptied.
- `SchemaCapabilities::driver()` names the engine a capabilities object describes. Capability answers are not a driver encoding, and reading them as one is a defect waiting for a capability to move: the admin schema pages derived `mysql`/`pgsql`/`sqlite` from `supportsNativeEnum()` and `supportsTransactionalDdl()`, which worked only while those two happened to separate the three engines and would have relabelled every SQLite database as PostgreSQL the moment SQLite's transactional-DDL answer was corrected. They now ask for the driver.
- Portable schema vocabulary for the two things hand-written DDL could say and the schema layer could not. `SchemaColumnType::BigText` compiles to `LONGTEXT` on MySQL — four gibibytes, against the 65,535 **bytes** of `Text` — and to `TEXT` on PostgreSQL and SQLite, which is already their widest; it is what a serialized job payload, saga context or integration event body needs, where `Text` would reject the write or silently truncate it past 64 KB. `SchemaCollation` states how a table compares the text it stores, with `Exact` emitting `COLLATE=utf8mb4_bin` on MySQL so two identifiers differing only in case or accent cannot collide on a `PRIMARY KEY` under the server's case-insensitive default (`utf8mb4_0900_ai_ci` and friends); PostgreSQL and SQLite are already exact and emit nothing. `Exact` has no case-insensitive counterpart and will not gain one: PostgreSQL has no table-level spelling for case-insensitive comparison, and SQLite's `NOCASE` folds ASCII `a`-`z` only, so the layer would be accepting a request it can honour on one engine of three — case-insensitive matching belongs in the query or in a generated column, where it is visible. Reachable through `Blueprint::bigText()`, `Blueprint::collation()`, `ColumnBuilder::collation()`, and the `collation` parameter on `TableDefinition` and `SchemaColumn`; both are used by the six framework tables above, and `tests/Contract` asserts the resulting type and collation against each engine's own catalogue rather than inferring them from a successful round trip, which passes on the narrow, folding shape too. Documented in [docs/database.md](docs/database.md#schema-builder).

- **Compliance evidence is collected, on the interval the config declares, into a file that survives the process.** `ComplianceVerificationEngine` accepts an `EvidenceChain` and had never been given one, so `recordEvidence()` returned at its first line on every run and a deployment's tamper-evident evidence trail was the empty set; `verification.evidence_interval` was read into `VerificationConfig` and consulted by no scheduler at all. `ComplianceVerificationWiring` now builds the chain over the new `FileEvidenceStore` — append-only JSONL beside the audit trail, through `WritablePathGuard`, in-memory only where `observability.audit.enabled` is off — keyed from the master key under the new `SubKeyId::ComplianceEvidenceChain`, and registers `EvidenceCollectionJob` (`compliance:collect-evidence`) on a cron expression derived from the interval and never rounded up past it. Without `PULSAR_MASTER_KEY` there is no chain and the boot log says so, rather than storing records anyone could forge. The boot check deliberately records nothing (`ComplianceVerificationEngine::withoutEvidenceRecording()`): the kernel boots once per request under PHP-FPM, and one signed record per request is not an evidence trail.
- **`pulsar data:purge` and the `data-protection:purge` scheduled job.** Every retention period in `config/data_protection.php` was read at boot, turned into policies, handed to a `DataPurgeOrchestrator` — and applied by nothing: no command resolved the orchestrator and no scheduler held a job for it. Storage limitation (GDPR Art. 5(1)(e)) is not satisfied by an intention to delete. The new `DataRetentionWiring` registers the job from `purge.schedule` (default `0 3 * * *`; `''` registers no job at all, keeping the policies without automatic deletion), and `data:purge --dry-run` counts without deleting whatever `purge.dry_run` says. Nothing is deleted until the operator enables the scheduler and runs `scheduler:tick`.
- `PasswordPolicyCheck` and `BreachNotificationCheck`, the first implementations of `ComplianceCheckInterface` in the framework — an extension point whose `checks` array `ComplianceVerificationWiring` had never populated. Each reads a `ComplianceProfile` field that no wiring, validator or reporter had read: `passwordMinLength` is reported against the floor Pulsar's own signup surface enforces, and never as a pass above it, because an application's password policy is not observable from this process; `breachNotificationHours` is measured against the incident register, failing the report for each incident at or above high severity that has outlived the deadline, and saying plainly that it cannot see whether a notification was sent.
- **The EU AI Act is a mapped framework, and the obligation Pulsar carries is Article 50.** Pulsar mapped eighteen frameworks, ISO/IEC 42001 — a voluntary AI management standard — among them, and not the binding law on the same subject. The gap mattered more than it looked: the digital omnibus in force since 27 July 2026 deferred the high-risk chapter to 2 December 2027 (Annex III) and 2 August 2028 (Annex I), and left **Article 50 transparency untouched at 2 August 2026**, so the chapter most deployments prepared for no longer binds while the one nobody prepared for is in force. `ComplianceFramework::AiAct` and `AiActMapping` add 22 controls of which **twenty name an operator artefact rather than a probe** — almost every AI Act duty is discharged in conduct or documents no framework observes — and the deferred Chapter III controls are declared stating **BINDS FROM** their own date rather than graded as present failures. `AiActRequirements` deliberately implements none of the `Has*` interfaces: every article that would justify a retention or encryption floor sits in Chapter III, and since `ComplianceProfileResolver` takes the most restrictive value across enabled frameworks, asserting one today would ratchet an unrelated control on the authority of an article binding nobody. For Article 50 the `ai-governance` extension gains `AiTransparencyInterface`: a surface declares whether it interacts with natural persons, what it generates and which exemption it relies on, and `AiTransparencyPolicy` **refuses** a declaration Article 50 does not permit — including the law-enforcement exemption on a surface available to the public to report a criminal offence, which Article 50(1) carves back out of it in terms. The four exemptions each discharge only the paragraph granting them, so obviousness never leaves a generated video unmarked. `SyntheticContentMark` states in its first paragraph that it marks **at the delivery boundary** and is not a watermark: the machine-readable and detectable limbs are delivered in full as an RFC 8941 assertion leading with `ai-generated=?1`, and the robustness limb for media is the integrator's, via a provenance standard such as C2PA. One control is probed (`ai-act-art-50-capability`, that positions can be declared at all); whether a person saw the notice and whether real output carried the mark stay operator artefacts. Two candidate observations were written and removed before shipping — one was always true because the constructor already refuses otherwise, the other cannot be measured because `ComplianceScope` produces only `Asserted` observations. See [ADR-0058](docs/adr/0058-the-ai-act-obligation-that-binds-is-article-50.md).

- **Every gate carries a negative test, and the list of gates is derived rather than typed.** An audit found **nine gates that could not fail**, each discovered separately and each green the whole time: a script that read a file which does not exist and exited 1 without checking anything; a Semgrep ruleset whose own header said `NOTHING IN CI RUNS THIS FILE`; `composer qa` cited in CONTRIBUTING.md as the mandatory gate and executed by no workflow; a ratchet whose `git grep` skipped the untracked files it existed to catch; a benchmark asserting 500 microseconds inside a job named "Hard Gate" that executed **zero wirings**. A tenth was found while enumerating the other nine — ci.yml's "Verify pipeline manifest integrity" computes a sha256 and compares it to nothing. One proposition covers all of them: **a check that has never been observed to fail is indistinguishable from no check**, which is [ADR-0041](docs/adr/0041-the-token-vault-takes-a-connection.md)'s thesis applied to the gates instead of the code they guard. `tests/Unit/Tooling/PipelineGateCoverageTest.php` now enumerates the pipeline and fails when a gate has no negative test. The gate list is **derived** from four declarations the repository already maintains — the leaves of `composer qa` expanded through `@` references, first-party scripts invoked by a workflow step that can fail the build, checkers sitting beside them (found by whether they can exit non-zero), and the composer, pnpm, analyzer-rule and baseline-ratchet targets — because a hand-maintained list is the same defect one level up, and this repository has already been bitten by it twice. The scanned directories are not configured either: they are wherever those sources found something, so a gate added in a directory nobody has thought of is discovered through its own invocation. Coverage is claimed with `#[GuardsGate(gate:, plants:)]` **on the test**, never in a list beside it, following the `# qa-gate:` precedent — a list beside it is a second definition that drifts, which is what `CompositionRootsAuthorityTest` exists to prevent one level down. Three further properties are pinned rather than assumed: a declaration must still contain an assertion that watches something refuse (so deleting the failing case and keeping the passing one stops satisfying it), the set of steps carrying `continue-on-error: true` cannot change unnoticed (a step that gains it stops being able to fail while keeping the name that says it can), and the set of third-party actions with authority over the merge cannot widen unnoticed — `actionlint`, `zizmor` and the SLSA generator need a runner, OIDC minting or a real release event, so the blind spot is recorded rather than omitted. Sixteen existing negative tests gained their declaration; seventeen gates carry an `UNFALSIFIABLE` or `PENDING` entry stating the reason and, for `PENDING`, what writing the test would take, capped by `EXEMPT_CEILING` so the list can shrink freely and grow only through a visible diff. Ratchets under `tests/Unit/Integrity/` are enumerated the same way by `GateNegativeCoverageTest`. See [ADR-0060](docs/adr/0060-a-check-never-observed-to-fail-is-indistinguishable-from-no-check.md) and the new "Adding a gate" section of [CONTRIBUTING.md](.github/CONTRIBUTING.md).

### Changed

- **A compliance fact can only be produced by the component that measures, and only a measurement proves behaviour.** Two holes remained in [ADR-0045](docs/adr/0045-a-control-status-is-observed-not-written.md) and three adversarial reviews walked through both using nothing but public `#[Api]` factories. `ControlEvidence::__construct()` was public and recorded no provenance, so fifty-one composed observations were indistinguishable from a gathered set and everything downstream inherited their authority; `ExecutedSubject::passed()` was a caller-supplied boolean spelled as a method name; `Inspection::membership()` ran `in_array()` over a roster the caller wrote. Every class under `src/Compliance/Control/` now has a private constructor, and every factory that produces a fact refuses a caller not compiled from `src/Compliance/Evidence/` — decided by file, not by namespace, because a namespace is something any file can declare. `__wakeup`, `__unserialize`, `__set_state` and `__clone` refuse as well. Reflection still reaches the private constructors and is the acknowledged escape the tests use, through one file that says so. Separately, `ObservationGrade::provesBehaviour()` is now true for `Measured` alone: `Resolved` computes `in_array($concrete, $accepts)` — which class is bound, and is it on the allow-list — which is ADR-0041's defect one lookup deeper. **Breaking for the report, not for the deployment:** probed coverage on a fully-equipped deployment falls from 78/96 to 32/96, and every control that moved now reads "Claimed and not observed", names the class that was found and its grade, and carries a remediation saying what would close it. No measurement was invented to keep a control green. `ProbeVerdict`'s summaries are generated from the deciding observations rather than from the constant `'Observed working, on %d required fact(s)'`, which used to be emitted even where nothing had been executed. `CoverageSummary`'s six-integer public constructor is replaced by `CoverageSummary::over($findings)`, so the one number an operator reads first is a tally rather than an argument. See [ADR-0050](docs/adr/0050-a-fact-is-produced-only-by-the-component-that-measures.md).

- **`deploy:check` refuses a deploy on any error-severity result.** It exited 0 with seven errors — including `FAIL debug-mode` and `FAIL master-key` in production — and printed "Use `--strict` to enforce a non-zero exit code", while `.env.production.example` told operators those two gates "fail closed … so the deploy is refused rather than warned about". The claim is now true: an error exits 1. `--strict` means the one stricter thing left, treating warnings as errors, which is also what it means on `studio:console:guardian:deploy:check`, so the flag has one meaning across the tree instead of three. To stop a check from refusing a deploy, lower its severity in `config/deploy.php` — a decision that appears in a diff, unlike a flag omitted at the call site. **Breaking for pipelines** that ran it without `--strict` and read the exit code: they were gating on nothing and will now fail on real errors.
- **The shipped `enabled_frameworks` is `[Gdpr]`.** It was seven — PCI DSS, GDPR, HIPAA, SOC 2, NIS2, ISO 27001 and ISO 42001 — which, since enabling a framework _is_ the claim that the deployment must satisfy it, made every Pulsar installation assert on day one that it was subject to all seven. `compliance:report` failed with 42 controls claimed and not shown. GDPR is the framework a default installation is held to. Two of its four probed controls are observed — Art. 5(1)(f) and Art. 32, from libsodium being exercised and the key hierarchy actually deriving — and two are not: ADR-0050 below withdrew resolved identity as proof, and Art. 25 and Art. 33 had rested on `PseudonymizationServiceInterface` and `IncidentReporterInterface` resolving to durable implementations that nothing ever exercises. `composer compliance:check` fails on a default installation because of those two, and the failure is left standing rather than configured away. `config/compliance.php` names, framework by framework, the specific fact a default installation does not deliver — the missing `token_vault` migration for PCI DSS Req 3.4, the absent backup contract for HIPAA and SOC 2, the untagged routes for ISO 27001 A.8.3 — so adding one holds no surprises. See [ADR-0046](docs/adr/0046-a-claim-is-something-the-installation-delivers.md).
- `IncidentReporterInterface` defaults to `FileIncidentReporter`, written beside the audit trail, instead of `InMemoryIncidentReporter`. Every incident the threat-detection engine, audit anomaly detector, access-pattern monitor and break-the-glass middleware recorded was lost at the end of the request that recorded it, and a register that empties on restart cannot evidence a GDPR Art. 33 (72h) or NIS2 Art. 23 (24h) deadline it cannot outlive. The comment it replaces read "override with `FileIncidentReporter` via config"; no such config key existed. In-memory remains the fallback where `observability.audit.enabled` is off — a deployment that keeps no durable security record at all.
- `DataPurgeInterface` is bound to the `DataPurgeOrchestrator` the wiring already constructed. It had been registered under its concrete class name only, so constructor injection of the contract — the framework's own rule — resolved nothing, and the compliance report read "nothing in this deployment erases personal data on request or on schedule" while the orchestrator sat in the container.

- `SchemaCapabilities::supportsTransactionalDdl()` reports what the engines do. It answered `false` for SQLite, and SQLite has transactional DDL — a `CREATE TABLE`, `ALTER TABLE ... ADD COLUMN`, `CREATE INDEX` or `DROP TABLE` issued inside a transaction is undone by `ROLLBACK`, and a DDL statement neither ends the transaction nor commits the rows written before it. The claim had never been executed: it was only ever compared to a value written beside it in a unit test. `tests/Contract/TransactionalDdlContractTest` now performs the experiment against every configured engine, so the entry cannot drift back. MySQL still answers `false` and is the only engine that does. Two behaviours follow. `SchemaManager` and `SchemaBuilder` wrap a multi-statement change in one transaction on SQLite, so a `createTable()` whose trailing `CREATE INDEX` fails no longer strands a bare table — asserted by `tests/Contract/SchemaAtomicityContractTest`. And the admin schema builder stops showing SQLite operators the `NO_TRANSACTIONAL_DDL` warning ("Schema changes are not atomic on this database driver"), which was simply untrue there. Migration runs are unaffected: `MigrationRunner` never consulted the capability and has always wrapped `up()` and `down()` unconditionally.

- Anti-spam proof of work is now exclusively the signed, single-use, TTL-bound Managed Challenge. The legacy client-controlled proof-of-work check accepted any client-minted `(challenge, nonce)` pair with no signature, expiry, or replay tracking — a solved pair was replayable indefinitely — and has been retired in favour of the audited managed-challenge engine. **Breaking:** the `#[Api]` `ProofOfWorkVerifierInterface` is removed, `AntiSpamConfig` no longer exposes `proof_of_work_enabled`/`proof_of_work_prefix`, and `AntiSpamContext` drops the `powChallenge`/`powNonce` constructor parameters. Enable `captcha_provider: 'managed'` for invisible proof of work; the CMS contact form now renders the `@shield` widget and verifies the solved token through the `#[Api]` `CaptchaVerifierInterface`.

- No core storage installs its own schema any more. `DatabaseSagaStateStorage`, `DatabaseWorkflowStorage`, `DatabaseTransitionLog`, `DatabaseFailedJobRepository` and `DatabaseOutboxPort` lose their `installSchema()` methods (and the outbox its unused `migrateSchema()`); they read and write tables that migrations create, so the runtime database role no longer needs `CREATE` and every schema change is recorded in the migration trail (ADR-0043). **Breaking:** `EventWiring` called `DatabaseOutboxPort::installSchema()` on every boot, so a deployment with `outbox.enabled` got `outbox_events` for free — it no longer does. Run `php bin/pulsar migrate:run` before the new build serves its first request, or the first `OutboxPort::store()` fails on a missing table. The other four installers had no production caller, so no other subsystem changes behaviour: those tables were never created automatically for anyone.

- Content blocks can stamp the request CSP nonce. `BlockRenderer::render()`/`renderRawBlocks()` accept an optional nonce that is exposed to blocks via a `_csp_nonce` render-context key (propagated through nested columns), and `ContentController` forwards the request's `csp_nonce` attribute. The contact-form managed-challenge widget now stamps it on its `<script>`, so the form also works under a strict nonce-based CSP — matching the `@shield` directive (the widget script is same-origin, so it was already `script-src 'self'` clean without a nonce).

- `DataPurgeOrchestrator` implements `DataPurgeInterface`. `SecurityWiring` had bound it under that contract on the strength of a comment claiming it did, so a consumer following the framework's own constructor-injection rule got an object that fataled on `purge()`. A single-category purge now delegates to the handler registered for that category and returns 0 where there is none, matching what `purgeAll()` already did for the same case.
- `CustomControlRegistry` is bound by `ComplianceWiring` and resolved by `ComplianceVerificationWiring`, instead of being constructed privately inside the latter. It was documented public API for organisation-specific controls and reachable by nobody: `verifyAll()` iterated a fresh empty instance on every boot. The engine now holds the container's instance rather than a copy, so a control registered after boot appears in the next verification run.

### Security

- **`league/commonmark` is required at `^2.10.2`.** `^2.8.2` admitted versions covered by six advisories, among them an XSS through the `on*` filter of `AttributesExtension` and a `DisallowedRawHtml` bypass reaching 2.10.1. The lock resolves 2.10.3.

- **The extension sandbox no longer costs the framework's own extensions their function, and the boot that proves it runs as a test.** Two consecutive rounds of hardening shipped having broken bundled extensions, both times found by reading rather than by running. Booting the framework with its thirteen bundled products enabled, at the tiers `config/extensions.php` grants them, found eleven distinct breakages. **At boot:** seven host services no extension could reach because nothing classified them — the role registry, the event listener provider, the import/export registry the kernel binds expressly for `postBoot()` registration, the incident reporter, the anti-spam pipeline and its AI-crawler settings, and the business-profile provider. The four that are host REGISTRIES an extension contributes to are priced at `ServiceRegister` rather than safe-listed, because a registry that hands back what other extensions put in it is not inert: `getProvider('users')` returns another extension's exporter, ready to invoke. **Two extension-to-extension integrations** refused for want of any rule about peers — `pulsar/forum` registering its resources through `pulsar/admin`'s `AdminGateway` and its member pages through `pulsar/cms`'s `AccountSectionRegistry`. An extension's `provides.services` list is now its public surface: a type named there, and physically shipped in that extension's directory, is resolvable from any other extension's scope, and everything else it ships stays private. The file decides and the name does not, so a manifest cannot publish a class its extension does not ship, and the consumer declares nothing — a rule satisfied by the consumer adding a line to its own manifest would constrain the honest and nobody else. **`pulsar/cms` could not boot at the tier this framework ships it at:** the catch-all a CMS is built around was refused by a tier comparison (`tier === Verified`) that contradicted the capability table beside it, which grants Verified the `RouteRegisterGlobal` the refusal named — the same shape as the `MiddlewareRegister` defect this round already fixed, and it stopped the CMS 166 routes short of its table while still reporting `Booted`. The check asks the policy now, and a catch-all still cannot ANSWER a reserved path: a negative lookahead is compiled into the parameter's constraint, because the literal reserved-path check cannot see a route that names no reserved path and matches all five.
- **`has()` on a sandboxed container answers for the scope, and five bundled controllers no longer 500 on the first request.** `ScopedContainerProxy::has()` reported the HOST's binding table and was documented as never lying about existence; it was the lie. PSR-11 defines `has()` as "can this container return an entry", and the scope cannot return `MasterKey` to a Verified extension — it throws — so `if ($c->has($x)) { $c->get($x); }`, the one idiom PSR-11 exists to support and the guard every bundled extension uses to degrade around an optional service, was a trap. It is why `pulsar/cms` could not finish registering. Answering for the scope also stops `has()` being a free map of which crypto, database and audit services a deployment has wired, readable by a tier that may resolve none of them. Separately, containment by construction had moved route-handler construction into the extension's scope, so a controller's constructor parameters are checked when the first request arrives, long after `boot()` reports success: `pulsar/forum`'s sign-in, registration and password-reset pages, `pulsar/cms`'s business-profile settings and `pulsar/payments`' checkout were all denied there while every boot-time check passed. The password hasher is priced at `CryptoOperations`, the tenant context at `DatabaseRaw` (`set()` re-points every tenant-scoped query — the same power as raw SQL by a shorter route, granted to the same tiers), and the authentication guard at a new **`AuthGuardAccess`** capability, added because nothing in the model named a power the framework plainly has: a holder can `login()` an identity it constructed. Safe-listing it would have handed that to Untrusted; pricing it at a borrowed capability would have made `config/extensions.php`, the record ADR-0023 asks an auditor to read, record the wrong decision. `pulsar/cms`, `pulsar/payments` and `pulsar/analytics` receive `additional_capabilities: ['CryptoKeyAccess']` — each derives keys from the master key, and two of the three would not have failed at boot at all, because a lazily-bound factory and a `has()` guard defer the failure to the first idempotent payment and to an analytics extension that silently tracks nothing. `tests/Integration/Extensibility/BundledExtensionContractTest` now boots the framework with its own extensions twice — once sandboxed, once with every extension at Core — resolves every route-handler class and every id each extension bound, and fails on anything the sandboxed boot delivers less of. **Upgrade note:** route names and the compiled catch-all pattern both changed, so a strict route cache built by an earlier build will not match; run `pulsar optimize` once on upgrade, which deployments already do. See [ADR-0023](docs/adr/0023-extension-trust-tiers.md).
- **An unauthenticated caller cannot grow the audit chain, and a route that cannot be served is diagnosed once instead of once per request.** Closing the unauthenticated existence oracle moved the missing-identity check in front of the resolver and the audit call went with it, so under a regulated preset - the default - every anonymous request to every bound route became one HMAC chain advance plus one `LOCK_EX` append, with the request path as the resource. The repair that followed, `AnonymousDenialLedger`, was worse than the defect: it capped the chain at 64 distinct `(route, reason)` shapes and past the cap refused **every** shape, so a caller who could reach 64 route shapes silenced every anonymous denial after them, legitimate ones included - an audit-suppression switch reachable without credentials. It also bounded nothing under PHP-FPM, where each request is its own process: measured at 300 chain records from 300 anonymous requests, against 1 from 300 in a persistent worker. It is deleted rather than resized, and the split is drawn at attribution instead. A denial that **names an actor** is chained in full, one entry per occurrence, with no ceiling and nothing in front of it - and a failing sink no longer causes a denial to be skipped, because the ledger claimed a shape before writing it and therefore retried a permanently failing chain exactly once, ever. A denial decided with **no identity** writes nothing to the chain and nothing to disk; it increments `pulsar_model_binding_anonymous_denials_total{route,reason}`. Not because the chain cannot hold an anonymous actor - `AuditActor::anonymous()` is a first-class constructor and the framework uses it elsewhere - but because nothing was accessed (measured: 0 resolver calls over 11,000 anonymous requests), because an entry per request lets the caller decide how far the chain grows, and because every such entry is the same entry. Both labels come from the route table, never from the request: a `Counter` keys a per-label map in memory, so a path label would rebuild the unbounded key space inside the process. `AuthorizationMiddleware` takes the same treatment on `pulsar_auth_anonymous_denials_total`, without which the change would be cosmetic on the routes a regulated preset is for - it refuses the anonymous caller one frame further out. The same defect appears once more in the log: a `500` out of `ModelBinder::plan()` is read off declarations, memoised and rethrown unchanged, and the middleware logged it at `error` with a stack trace on every request to a route an unauthenticated caller can reach - measured at 2,270 bytes and 743 us per request over 2,000 requests, uncapped. `BindingResolver` now announces it once, at `error`, on the one pass that decides it, and `ModelBindingMiddleware` counts the request on `pulsar_model_binding_refusals_total{route,status}` and drops its own line to `debug` without the exception: 1 line and 2,065 bytes for the same 2,000 requests at production log levels, and 20-41 us per request against 743-756. That is an aggregation and not a ceiling - there is no capacity and no claim, the deduplication is the resolver's existing memo, and no number of broken routes can stop the next one being reported. An anonymous request costs the same whether the row exists or not, measured over ten runs of 5,000 interleaved A/B pairs: largest delta 0.4 us at p50 on a 21 us request, sign changing four times. **Breaking** for anything constructing `ModelBindingMiddleware` or `BindingResolver` directly (both `#[Internal]`): each gained one trailing optional constructor parameter, and `Pulsar\Routing\Binding\AnonymousDenialLedger` is removed. `MetricRegistry` is declared an optional binding of `ModelBindingWiring`, so a deployment with `observability.metrics.enabled` off is told it is not reporting these counts rather than discovering it when somebody asks for the number. See [ADR-0056](docs/adr/0056-an-unattributable-denial-is-counted-not-chained.md).

- **The compliance evidence chain resumes across processes, and its signature covers the fields an auditor reads.** Two defects in the chain that was wired earlier in this cycle, each of which made the tamper-evidence claim false in a different direction. (1) `EvidenceChain::__construct()` seeded `previousSignature` from the genesis label unconditionally and never consulted the store, so every process started a fresh chain at genesis — and `scheduler:tick` is a new process per tick, so from the second collection run onward `verifyChain()` reported the deployment's own record as tampered. The chain now resumes from the stored tail through the mechanism `AuditLogger` already uses for the audit chain: the new `EvidenceChainStateAware` sub-contract (implemented by `FileEvidenceStore` and `InMemoryEvidenceStore`) reports the store as `Empty`, `Healthy` or `Corrupted` using the audit log's own `AuditChainState`, and the tail's own signature is re-verified before it is trusted as a predecessor. (2) The record signature covered `$record->data` and nothing else, so `description` — the sentence stating how many checks passed — along with `collected_at`, `id`, `control_id` and `type` sat outside the HMAC and could be rewritten while `verifyChain()` still reported the chain valid; the fields the record exists to protect were the ones it did not protect. The signed message is now length-prefixed over every field, the encoding `AuditEntry` uses, and carries a `signature_version` and a key commitment (`chain_genesis`) inside the signature. **When the stored chain cannot be verified under the key in service, the chain refuses to append** and throws `UnverifiableEvidenceChainException` rather than guessing: a key rotation, a restore from another deployment's backup and a genuine tamper are indistinguishable from inside the process, and both alternatives to refusing — chaining onto an unauthenticated record, or re-seeding from genesis — produce a chain that verifies across a period in which the evidence did not. Recovery is an operator act: archive the register and start a new chain, or restore the key that signed it. `ComplianceVerificationEngine` catches the refusal at the recording seam, so a refused append still never discards a completed verification report. Separately, `ControlEvidenceGatherer` now verifies its bounded re-verification window against the signature of the record preceding it instead of against genesis, which had reported a false break on the window's own first record for every deployment whose chain outgrew the 500-record limit. **Breaking for stored records only, and none shipped:** records written by the unversioned format do not verify and are reported as broken rather than guessed at.

- **Route model binding cannot mint an attestation without an authorization decision, and an attestation stops at the request that earned it.** Three holes in the seal, closed together because they are one hole with three entrances. (1) `ModelBinder::bind()`/`bindWithMeta()` took `?Closure $authorize = null` and minted a `BindingProvenance` entry for every model regardless — so provenance, the evidence `BoundModelArgumentResolver` seals a handler argument on, was produced whether or not anything had decided the caller may have the row, and every way of reaching the binder without a gate (a default argument nobody passed, a hand-built binder, a caller who forgot) produced a model carrying the same evidence an authorized one carries. The parameter is now a required `BindingAuthorization`: either a policy gate, or a named exemption that verifies its own declaration — `declaredWithoutAuthorization()` refuses a route without the `_without_authorization` attribute and `unenforcedPreset()` refuses a regulated preset — so under a regulated preset, for a route that declares no opt-out, the only decision that can be constructed is a gate. The decision also names the route it was made about, and binding another route with it is refused, so an exemption legally obtained for a public route is not a value that binds anything else. (2) `ModelBinder` was registered in the container while `bindWithMeta()` is public, so anything holding the container could load a row through the application's own `ModelResolverPort` and mint provenance for it — the seal forged a step earlier than the attribute it exists to distrust. It is no longer bound; `ModelBindingWiring` hands the one binder it builds to `ModelBindingMiddleware` as a private property. (3) An attestation was keyed on instance, parameter and URL value only, and objects outlive requests: any persistence layer with an identity map hands the same instance to every request that asks for that row, so a model one caller resolved and was authorized for could be dropped into `_bound_models` on a later request — most easily on a route that binds nothing, where the binder never runs to contradict it — and sealed onto a handler serving somebody else. Entries now name the binding pass they were minted in, and `ModelBindingMiddleware` opens one at the top of every request it sees, before any early return. The pass is a counter held inside `BindingProvenance` rather than anything carried on the request: PSR-7 clones on every `withAttribute()`, so the binder's request and the resolver's are different instances, and an attribute is the surface the seal exists not to trust. It relies on [ADR-0010](docs/adr/0010-persistent-worker-runtime-request-sandbox.md)'s guarantee that a worker serves one request at a time. **Breaking** for anything calling `ModelBinder` directly (`#[Api]`, unreleased): the fourth argument is required and typed, and the class is no longer resolvable from the container.

- **An unentitled caller can no longer tell an existing record from an absent one.** The acceptance criterion was "anonymous OR unentitled" and only the anonymous half was met: an authenticated caller the policy hook refused was answered `403` where a caller asking for a row that does not exist got `404`, so anyone with an account and no entitlement could walk the id space of a bound route and read off which ids are real — and on a nested route learn it about the PARENT, since the parent is fetched to scope the child. Ordering cannot close this half, because a policy answers "may this caller have THIS record" and needs the record; the answer closes it instead. `ModelBindingException::authorizationFailed()` now carries `404`, so a refused caller receives the same status, reason phrase, headers and body a missing row produces. Nothing is lost from the diagnosis: the denial is still recorded in the audit chain as `policy_denied` with the actor, the model class and the parameter, and the exception message naming the model and the key still reaches the log — both where an operator can read them and the caller cannot. The residue is timing, which no framework layer can equalise for a store. **Breaking** for applications that branch on the `403`; the illegal `_without_authorization` opt-out keeps its `403`, being a property of the route table that is identical for every caller and every id.

- **A sealed handler argument now carries where its value came from.** `BoundModelArgumentResolver` wraps every claim in a `SealedArgument`, which no other resolver may displace — and its whole evidence for doing so was the `_bound_models` request attribute, which any middleware inner to the binding one can write. So anything that could set one attribute got its own object onto a parameter typed as an entity **and** made it undisplaceable: "cannot be displaced" had become "was authorized", which is a stronger claim than anything upstream had made. The new `BindingProvenance` record closes it. `ModelBinder` writes one entry per model it resolves — the instance, the route parameter it was resolved for, and the raw URL value it was resolved from — and mints a level only after the authorization gate it was given has passed it, so a model the hook refused is never recorded. The resolver seals only what that record attests. `ModelBindingWiring` composes both halves from one instance and binds neither it nor the binder in any container, so the write side is reachable only through a private property of a private property. An object with no entry is not claimed at all, sealed or otherwise: the parameter falls through to the route value or its default, exactly as on a route that binds nothing. Because an entry names the parameter and the URL value, a model the framework produced for `{post}` = 41 cannot be replayed for `{post}` = 9 or onto another parameter of the same route. **Breaking** for anything constructing `BoundModelArgumentResolver` directly (`#[Internal]`): it now requires a `BindingProvenance`, and `ModelBinder` takes one as a trailing optional constructor argument.

- **The kernel's argument-resolver chain cannot be replaced through the container.** `ArgumentResolverChain` is published there so a wiring can `add()` to it, and `restoreFromSnapshot()` — the boot/shutdown capability that stops a re-booting worker stacking a second copy of every resolver — was a public, unguarded mutator on the same object. Replacing the list is strictly more than appending to it: an appended resolver is refused a sealed name by the merge rules, while a replacement removes the sealing resolver and with it the seal, so anything that could reach the container could drop `BoundModelArgumentResolver` and take a bound route's parameter with an ordinary claim. The capability is now a single `ArgumentResolverLifecycle` handed out by `ArgumentResolverChain::issueLifecycle()`, which the kernel takes in its constructor — before any wiring, extension or route file runs — and refuses to issue twice (`ArgumentResolverLifecycleException`). `Kernel` holds it in a private property and binds it nowhere. **Breaking** for anything calling `ArgumentResolverChain::snapshot()`/`restoreFromSnapshot()` (`#[Internal]`); both live on the handle now.

- A handler parameter typed `object` or `mixed` receives its bound model. `HandlerParameter::accepts()` answered "accepts nothing" for both — it refused every builtin type name, and `instanceof` cannot see that `object` and `mixed` accept every object there is — so `show(object $post)`, the shape a controller takes when the entity class is generated or when one handler serves several, was handed the raw URL string instead of the resolved, authorized entity. Silently, with a 200, after the containment and policy checks had run and their result was discarded one frame before the handler. `iterable` and `callable` are answered the same way PHP answers them: accepted for a `Traversable` and an invokable object respectively, refused otherwise. Every other builtin still takes the raw route value, so a scalar parameter that shares a route parameter's name is untouched.

- **An authorization decision no longer runs the application.** The wiring that made `Gate::allows()` record its decisions dispatched them through the application's `EventDispatcherInterface`, and `ListenerProvider` keys listeners by the dispatched object's class — every envelope is an `EventEnvelope` — so **every** listener the application had registered for envelopes ran inside **every** authorization decision. `EventDispatcher` re-throws the first listener error after its loop, so an unrelated listener with a bad day turned an allowed request into a `500`; a slow one made every authorization check slow; and one that asked the Gate a question re-entered `allows()` → dispatch → itself, bounded only by `StormGuard` throwing — which unwound the outer decision after its nested ones had already been written, leaving the audit trail holding the consequences of a decision it had no record of. Measured, the dispatcher took a decision from 4.0 µs to 58 µs, and to 60 µs with twelve unrelated listeners also registered; `AuthorizationBench` never saw it, because every Gate subject in that file builds one that records nothing. The record stays and the mechanism goes: the Gate hands each decision to a single `AuthorizationDecisionSinkInterface` the composition root chooses, so nothing the application registers is on the authorization path at all. Everything the sink raises is caught and reported at `critical` rather than unwinding the decision, and a sink that calls back into the Gate is refused a nested frame — the decision it caused is queued and written after the outer one, up to a ceiling of 16, past which further nesting is refused and reported. `BufferedAuthorizationDecisionSink` captures the decision and the `RequestContext` it was made in and writes the HMAC-chained entries on the kernel's terminate event, after the response has gone out, or once `auth.authorization.decision_audit_buffer` (default 64, `1` for write-through) decisions are waiting: a grant now costs 4.3 µs against 4.0 µs before anything was recorded and a refusal 4.6 µs against 3.9 µs — the evaluation itself halved, which is what pays for the record, and `AuthorizationBench::benchGateAllowsRecordingDecisions` holds a 20 µs budget so the write cannot move back inside the decision unnoticed. The entry gains the correlation id of the request the decision was made in, where the old one carried a freshly minted random value that correlated nothing. **Breaking** for anything constructing `Gate` directly (not `#[Api]`): the third parameter is a decision sink, not an event dispatcher — and `AuthorizationGranted` / `AuthorizationDenied` are no longer dispatched to application listeners, which nothing released before 1.0.0-rc.11 ever did either. See [ADR-0052](docs/adr/0052-an-authorization-decision-does-not-run-the-application.md).

- **Every authorization decision the Gate reaches is now recorded.** `Gate::allows()` announces each grant and each denial by dispatching `AuthorizationGranted` / `AuthorizationDenied`, and both dispatch paths return early when no dispatcher was supplied — which is how `AuthWiring` had built it, so a framework whose compliance story is a tamper-evident HMAC-chained audit log wrote no authorization decision anywhere. `AuthorizationMiddleware`'s own optional logger covered only denials arriving through a route's `permissions` attribute; every decision reached by a policy, a service or a controller calling `allows()` directly left nothing behind. The wiring now passes the dispatcher **and** registers `AuthorizationDecisionAuditListener` in the same block — a dispatch nobody listens to is still not an audit trail — writing each decision as `AuditEvent::Authorization` with the permission, the reason (`super-role`, `RBAC`, `ABAC`, `ABAC-deny`, `default-deny`), the envelope's `payload_hash`, and the CSPRNG `decision_nonce` minted at decision time, so a rewritten record fails its hash and a replayed one is detectable rather than merely suspicious. A sink failure is reported at `critical` and never unwinds the decision that caused it. See [ADR-0048](docs/adr/0048-a-guard-is-something-a-request-runs-into.md) — the mechanism described here was replaced before release; see the entry above.

- **`AccountTakeoverGuard` is reachable.** It was constructed nowhere — no middleware, no wiring, no controller — so in every Pulsar deployment a password change, e-mail change, MFA disable, recovery-code regeneration or account deletion succeeded on the strength of a session cookie, from any address, on any device, however long ago the person last proved who they were. The new `sensitive` middleware alias runs it over a route that names the operation it performs (`attributes: ['sensitive_operation' => 'password_change']`), refusing a credential change that arrives from a different address **and** a different device, and refusing one made outside the re-authentication window — satisfied by either a fresh login or a completed step-up challenge, so a route already carrying `step-up` does not prompt twice. `SessionGuard::login()` now stamps when credentials were presented, distinct from the session's `createdAt`, which `regenerate()` carries across. Fail-closed throughout: an undeclared operation, a missing security context, an unauthenticated identity, absent session metadata, and an audit sink that cannot record the decision all produce `403`. Two defects only observable once anything executed the path are fixed with it — the guard recorded its verdict against `SessionMetadata::$userId`, which nothing in the framework populates, so a detected takeover reached `AuditLogger` with a null actor and destroyed the one record it exists to produce; and the middleware caught only the three exceptions `AuditLogger` declares, while a sink signals a failed write with `SecurityException`, so a full disk turned a refusal into a 500 and an ordinary address change into one too. No existing deployment is made safe by this alone: the framework cannot pick an application's credential-changing routes, and the remaining step is one route attribute — see [docs/authentication.md](docs/authentication.md#sensitiveoperationmiddleware-route-level).

- The route cache now carries the binding declarations the route table depends on, so route model binding's escape hatches exist in production. `Router::model($param, $class, scope: BindingScope::Root)` is the only way an application declares a deliberately unscoped nested child, and `scope: BindingScope::Contained, parentRelation: …` the only way it names a relation a path segment cannot spell — both called from `routes/web.php` or `routes/api.php`, which `Kernel::boot()` skips whenever a cached route table is loaded. Every such declaration was therefore erased by `pulsar optimize`: a `Root` became a scoped lookup through a relation that does not exist (404) and a named relation reverted to the path's (500). No read was ever widened, but a fail-closed scoping rule whose only escape hatch is unavailable in production is a rule an operator switches off rather than uses. `routes.cache.bin` now stores a `CachedRouteTable` — routes and declarations as one payload under one manifest signature and one invalidation key — written by `pulsar optimize` and applied by `Kernel::boot()` before the router is locked. A payload this build cannot read, or one whose stored declaration contradicts itself, is discarded whole and the boot falls back to reading the route files rather than serving routes whose declarations have gone. **Breaking:** `FrameworkCacheInterface::warm()` gained a trailing `array $bindings = []` (call sites are source-compatible; external implementors must adopt the parameter), and `CacheManifest::SCHEMA_VERSION` is 2 — a cache written by an older build is refused and rebuilt on the next `pulsar optimize`, which deployments should run as they already do.

- The route model binding preset can no longer fail open on a typo. `ModelBindingConfig::$preset` was a free-form string matched with a strict, case-sensitive `in_array` against `banking`/`healthcare`/`legal`, so `Banking`, `bankng` or `BANKING` missed the regulated branch and silently selected the permissive one — the application's authorization posture depending on its own spelling, with no warning anywhere. It is now the closed `Pulsar\Routing\Binding\BindingPreset` enum, and `ModelBindingConfig::fromArray()` converts through `BindingPreset::fromConfig()`, which throws a `ConfigException` naming the offending value and the four valid ones rather than defaulting. An unrecognized preset — including `null` and a non-string — now fails the boot during config load instead of reaching the request path as a permissive posture. `isRegulated()` is stated as "anything that is not `Standard`", so a preset added later enforces until someone deliberately exempts it. **Breaking:** `ModelBindingConfig::$preset` is a `BindingPreset`, not a `string`; config files are unaffected as long as the value is one of the four documented names.

- A nested bound route is no longer an existence oracle on the parent it is nested under. `/records/{record}/entries/{entry}` resolves outside-in — the record is fetched to scope the entry — and `ModelBindingMiddleware` authorized afterwards, over the finished map of resolved models. So a caller with no claim on the record still caused it to be read and the entry to be looked up inside it, and was answered `404` **naming the entry**, which only a record that exists can produce; against a record that does not exist the request failed one step earlier with a `404` naming the record, and the two were distinguishable without reading a status code. Worse, both threw from inside the binder, before the authorization pass began, so the hook had run for neither level even though the parent had been read. `ModelBinder::bindWithMeta()` now takes an optional authorization gate and calls it on each model the moment it resolves, before the next lookup starts: every level that is read has been decided, a refusal stops the walk there, and a model the gate refused is never recorded as a parent or minted as provenance. What a refusal at the parent still discloses is what the parent's own route already did — `403` for a record that exists, `404` for one that does not — so nesting adds no channel of its own. Asserted as an interleaved log of resolver and hook calls in `tests/Unit/Routing/Binding/NestedParentDisclosureTest.php`. `ModelBinder::bind()` and `bindWithMeta()` gained a trailing optional `?Closure $authorize`; existing call sites are unaffected.

- A binding refusal no longer repeats what it was asked, and carries the headers of a response that must not be cached or sniffed. The `404` and `400` bodies were the exception message, and every factory on `ModelBindingException` names the model class while three append the route parameter's raw value — so a miss answered `No [App\Domain\Patient] found for [id] = "4181"`: the internal class layout of the application handed to an unauthenticated scanner, beside the segment the scanner had just sent, in a plain-text response that set no `Content-Type` at all. The body is now the status' reason phrase, with no parameter through which either could reach it, and the message goes to the logger instead — `error` for the 500s, because each is a route that has never worked for anyone, `debug` for the client errors, because a `404` is ordinary traffic and an id scan must not be able to fill a disk through that line. This also publishes, for the first time, the diagnosis a scoping refusal writes: which parameters, and the three ways to fix the route. Every refusal now carries `Content-Type`, `Cache-Control: no-store`, `Vary: Accept`, `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer` and a `default-src 'none'` CSP — the set `ProductionRenderer` already gives an error built where no pipeline is guaranteed to decorate it, and a floor `SecurityHeadersMiddleware` overwrites where it is wired. **Behaviour change** for clients that parsed the old `404`/`400` bodies: they now read `Not Found` and `Bad Request`.

- Every authorization denial the binding layer makes now leaves an audit record. Two of the three left none: the `401` for a missing identity under a regulated preset and the `403` for an illegal `_without_authorization` opt-out were moved in front of the resolver to close the unauthenticated existence oracle, and the single `AuditLogger` call stayed behind with the hook — so the two refusals a regulated deployment sees most often were the two it could not show an assessor, while producing exactly the same HTTP response as a recorded denial. All three are now written as `AuditEvent::Authorization` / `AuditOutcome::Denied` with `action` = `model_binding_authorization`, the request path as the resource, and a metadata `reason` of `unauthenticated`, `authorization_bypass_forbidden` or `policy_denied`; a hook denial also names the model class and the route parameter, so a nested route records which level refused. A caller with no identity was recorded under the actor `anonymous` — the literal `AuthorizationMiddleware` already used — rather than anything derived from the request, and an audit write that fails still refuses the request. The anonymous half of that was replaced before release: an unattributable denial is counted, not chained. See the entry above and [ADR-0056](docs/adr/0056-an-unattributable-denial-is-counted-not-chained.md).

- Build-artifact signatures are now actually verified at boot. `BuildArtifactVerifier` runs before `SecurityWiring` binds the crypto services, so it previously skipped signature verification whenever they were absent and fell back to hash-only checks — which an attacker with write access to `var/cache` defeats by tampering with an artifact and recomputing its hash. The verifier now bootstraps the HMAC + key provider from the master key itself (independent of wiring order) and is **fail-closed**: a signed `build-manifest.json` whose key material is unavailable refuses to boot rather than trusting the manifest on its hashes alone.

- **`pulsar/ai-governance` runs sandboxed, and one extension can no longer read another's configuration.** `config/extensions.php` granted the AI governance extension the `core` tier — the tier that bypasses both sandbox proxies and hands the extension the real container and the real router — on the recorded ground that below Core "the sandbox proxies the container, and its deny-by-default rule refuses any service id the framework's restriction map does not classify, which is every id an extension registers for itself", so its EU AI Act deployment gates "could not execute in a shipped deployment at all". That premise was false against the tree it was written for, and nobody had run it: an id the extension binds through its own scope is rescued by `ScopeRegistrations`, and a type it ships is rescued by `ScopedContainerProxy::isOwnCode()`, both consulted after the restriction map for exactly this case. Booting the extension at `verified` named the real defect on the first attempt, and it was a **host** service rather than any of the extension's own: `ExtensionConfigRegistry` — the object every bundled service provider reads its own `config/<name>.php` out of — was in no category of the restriction map and fell to deny-by-default. It took `pulsar/booking` and `pulsar/payments` down inside `boot()` as well, so the grant would not have fixed the class of bug even for the extension it was written for. The registry is now classified, and classifying it alone would have been the worse bug: **one** registry instance holds every extension's sections, and a real `payments` section carries a webhook secret and a provider API key, so a safe classification would have handed every tier holding `ContainerRead` — Untrusted included — every other extension's credentials in one call. The scope therefore exchanges it for a view narrowed to the sections the receiving extension itself ships, the third such exchange after the container and the router, with `ExtensionConfigRegistry::restrictedTo()` as its public form; the narrowing filters by section NAME, so an operator's override of that extension's own section still arrives and nothing else does. The `core` grant is withdrawn, the manifest's own `trust_tier` request drops to `verified` to match, and `ExtensionSandboxDriftTest` no longer carries a core-tier exception list for products at all. `ShippedDeploymentGateTest` boots the extension through `ExtensionSandbox::harden()` at whatever tier `config/extensions.php` actually grants and executes the Article 5 and Article 9/11/72(3) gates through the container that boot produced, so the next tier change is measured rather than argued — it fails, with instructions, if the tier ever goes back to `core`. See [ADR-0023](docs/adr/0023-extension-trust-tiers.md).

- **A concurrent authorization decision is no longer cross-attributed or dropped, the chained audit write is no longer inside `Gate::allows()`, and `pulsar optimize` no longer fails on the framework's own wiring.** Four defects in what ADR-0052 put in place of the event dispatcher, each of which made one of that ADR's claims untrue of the code implementing it. (1) `Gate::record()` guarded re-entry with `private bool $recording` plus a shared nested queue, which answers "is this Gate recording anywhere" and not "is this call stack inside a record" — and the sink `AuthWiring` binds reaches an `AuditLogger` that spins cooperatively on its chain lock, so a suspended sink is what the framework does under contention, not a hypothetical. Measured: a decision made by a second Fiber was handed to the sink on the _first_ Fiber's call stack, counted against its ceiling and named under its permission in the `critical` line; twenty Fibers deciding at once produced **seventeen** records, the last three refused past `MAX_NESTED_DECISIONS` and then discarded by the first Fiber's reset. The guard is now a `WeakMap` keyed by `Fiber::getCurrent()` — the mechanism `RequestContextHolder`, `TenantContext` and `RouteContext` already use — so the queue, the refusal count and the ceiling belong to one decision instead of to the Gate. (2) Both `critical` reports were made straight through the application's logger, one from the `catch` that contains a throwing sink and one from the `finally`; a logger that throws therefore put the contained fault back on the caller one frame out, and from the `finally` replaced whatever was being unwound. Every report on this path is now wrapped and cannot raise, which also makes ADR-0052's statement that the sink's destructor "cannot turn a clean exit into a fatal" true rather than nearly true. (3) `BufferedAuthorizationDecisionSink::record()` flushed the whole buffer the moment it reached its threshold, and the shipped threshold was 64 — so a request authorizing a row at a time paid for 64 HMAC-chained entries inside one arbitrary check. Measured over 300 decisions at the shipped configuration: **256 entries written inside a decision** before any drain point ran. `record()` now writes nothing; the entries are chained at drain points — the kernel's `TerminateEvent`, the queue's `JobCompleted` / `JobFailed`, and the sink's destructor — and `decision_audit_buffer` becomes the memory ceiling behind them rather than a batch size, defaulting to **1024** and reporting once at `critical` when reached before chaining one entry per further decision to stay inside it. `1` still means write-through, unchanged and unreported, because that is a configuration and not a defect. On a 200-decision request that moves the worst single decision from **4.34 ms to 36.6 µs** and the request's authorization cost from **12.10 ms to 1.26 ms**, for the same total work; an 8-decision request is parity. (4) `AuthWiring` registered the terminate flush as a **closure**, which `EventMapCompiler` cannot compile — so `php bin/pulsar optimize` exited 1 with "closures cannot be compiled" on every deployment that had an audit logger, before reaching anything the application had written. It is now `AuthorizationDecisionFlushListener`, an invokable `#[Internal]` class bound under its own name so the compiled map resolves the listener holding the configured sink. `AuthorizationBench::benchGateAllowsRecordingDecisions` — the subject ADR-0052 names as the guard against putting the write back inside a decision — was building its sink with `flushThreshold: 1_000_000`, a number no `config/security.php` ever contained; it now takes the capacity from `AuthorizationConfig::DEFAULT_DECISION_AUDIT_BUFFER` so it cannot drift from the shipped value again. **Breaking** only for code constructing the `#[Internal]` sink by named argument: `flushThreshold:` is now `capacity:`. See [ADR-0057](docs/adr/0057-a-guard-that-is-not-call-scoped-guards-nothing.md).

### Removed

- **`EntitySerializationGuard` is deleted rather than wired.** `ApiWiring` built it and bound it in the container; `check()` had no caller anywhere in the tree, so the "entities must never bypass the resource transformation layer" invariant its docblock states was enforced by nothing it did. It was not wired because the property is already structural and stronger without it: `Kernel::invokeHandler()` accepts a `ResponseInterface` or a string and throws `RoutingException::unexpectedReturnType()` for everything else, unconditionally and in every environment, so a controller returning a domain entity produces a refused request before any encoder is reached. Wiring the guard would have added a second check behind a check that cannot be got past — and put an `api.entity_serialization_ban` switch in front of a guarantee that currently has none. `EntityNeverAutoSerializesTest` now pins the kernel's behaviour so the reasoning fails loudly if a future change introduces an auto-serializing return path. **Breaking:** `ApiException::entitySerializationBanned()` (`#[Api]`), the `ApiConfig::$entitySerializationBanEnabled` constructor parameter (`#[Api]`), and the `entity_serialization_ban` key in `config/api.php` are removed; each existed only to configure a class that was never asked a question. See [ADR-0048](docs/adr/0048-a-guard-is-something-a-request-runs-into.md).

- **`EvidenceCollector` is deleted rather than wired.** It was the third evidence abstraction in the tree and the only one with no consumer at all — no wiring constructed it, nothing registered a collector into it, nothing called `collect()`. Wiring it would have been worse than leaving it: it writes `EvidenceRecord`s with `signature: null` into the same store the evidence chain uses, and `EvidenceChain::verifyChain()` reports every unsigned record as broken, so the second writer would have made the tamper-evident trail report itself tampered with. There is now one evidence writer and it signs. **Breaking:** `Pulsar\Compliance\Evidence\EvidenceCollector` (`#[Api]`) is removed; `EvidenceStoreInterface` and `EvidenceRecord` are unchanged, and `EvidenceType` gains a `VerificationRun` case (`verification_evidence`, the value already in stored records) so the vocabulary names what the chain writes.
