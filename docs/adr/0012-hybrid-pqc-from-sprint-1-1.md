# ADR-0012: Hybrid PQC (X25519 + ML-KEM-768 / Ed25519 + ML-DSA-65) from Sprint 1.1

* **Status:** Accepted
* **Date:** 2026-04-27
* **Driver:** Lenny Obez
* **Related Section II decision(s):** Decision 2.58 (Hybrid PQC from Sprint 1.1 — no classical-only window), Decision 2.53 (Kernel cryptographic primitives: HACL\* via FFI), Decision 2.20 (Formal verification scope), Section 14.1 (Post-quantum cryptography)
* **Sprint:** Sprint 0.9-bis (v2.3 reconciliation closure); implementation Sprint 1.1 (kernel crypto)
* **Supersedes:** Section 14.1 v2.2 phasing ("hybrid PQC at Sprint 1.5 after classical primitives") — now lifted to Sprint 1.1.

## Context

The harvest-now-decrypt-later (HNDL) threat is the canonical motivator for post-quantum cryptography (PQC) migration in 2026:

* An adversary records ciphertext + key-establishment metadata today.
* When a cryptographically-relevant quantum computer becomes available (NIST estimates 2030-2040 for RSA-2048; Curve25519 may follow earlier or later), the adversary retroactively decrypts the stored ciphertext using Shor's algorithm.
* Long-term confidential material (regulated PII, audit chains, encrypted-at-rest storage) generated today therefore carries a future decryption risk proportional to its retention requirement.

For Pulsar Framework's regulated-domain target (banking + healthcare + government + legal), retention requirements span decades:

* Banking transaction records: 7-10 years per Basel III + DORA + national banking regulations.
* Healthcare records: 6-25 years depending on jurisdiction (HIPAA + EU healthcare directives + national variations).
* Legal e-discovery archives: indefinite for active matters; 30+ years for closed cases.
* Government identity + qualified-signature material: lifetime + decades-after-death (eIDAS 2 qualified signature retention).

NIST finalised three PQC standards in **August 2024**:

* **FIPS 203** — ML-KEM (Module-Lattice-Based Key-Encapsulation Mechanism), based on CRYSTALS-Kyber. Three security levels: ML-KEM-512 (NIST level 1, ≈ AES-128), ML-KEM-768 (level 3, ≈ AES-192 — recommended baseline), ML-KEM-1024 (level 5, ≈ AES-256).
* **FIPS 204** — ML-DSA (Module-Lattice-Based Digital Signature Algorithm), based on CRYSTALS-Dilithium. Three security levels: ML-DSA-44, ML-DSA-65 (recommended baseline), ML-DSA-87.
* **FIPS 205** — SLH-DSA (Stateless Hash-Based Digital Signature Algorithm), based on SPHINCS+. Useful where ML-DSA's signature size is acceptable but mathematical-assumption diversity is desired.

HACL\* (per ADR-0009) ships ML-KEM-768/1024 + ML-DSA-65/87 with formal proofs as of 2026Q1. The integration cost in Pulsar is **negligible**: HACL\* exposes the same C ABI shape for classical and PQC primitives, and the Rust safe wrappers in `pulsar-kernel::crypto` can implement hybrid constructions trivially via HKDF combination (for KEM) or dual-signature concatenation (for signatures).

## Decision

Pulsar Framework integrates **hybrid classical + PQC primitives starting at Sprint 1.1** — the first sprint that ships any cryptographic primitive. There is **no classical-only Phase 1, hybrid-PQC-at-Phase-2 window**. Long-term secret material generated by Pulsar at any point in its history is safe against the harvest-now-decrypt-later threat.

**Key establishment (KEM):** every protocol that uses key encapsulation runs **X25519 + ML-KEM-768 in parallel** and combines the resulting shared secrets via **HKDF-SHA-256**. This matches Cloudflare PQ-Hybrid (production since 2023), Google Chrome PQ-TLS (since 2024), Apple iMessage PQ3 (since 2024), AWS KMS hybrid (announced 2025), and IETF draft-ietf-tls-hybrid-design.

```
shared_secret = HKDF(salt, X25519_secret || ML-KEM-768_secret, info, 32)
```

The hybrid construction inherits the security guarantees of **both** primitives — an attacker must break both the classical and the post-quantum primitive to recover the shared secret.

**Signatures:** every signature scheme that anchors a long-term commitment runs **Ed25519 + ML-DSA-65 in parallel**. Verification requires **both** signatures to validate. The dual-signature posture preserves classical-only verifiability for legacy clients (which can ignore the ML-DSA portion via standard signature-format extensibility) while gaining PQC protection for any verifier that checks both.

**At-rest encryption:** AEADs (AES-256-GCM, ChaCha20-Poly1305) remain symmetric and are not PQC-affected (Grover's algorithm against AES-256 still requires ~2^128 work — practically infeasible). Long-term key wrapping (KEK encrypting DEKs) uses hybrid key-establishment per the KEM rule above.

**Migration path:**

* `v0.1.0` → `v0.5.0`: hybrid PQC by **default** with classical-only fallback for legacy peers (with a runtime warning emitted to `pulsar-observability`).
* `v0.5.0` → `v1.0.0`: hybrid required by default; classical-only fallback opt-in via deployment-time configuration.
* `v1.0.0+`: PQC-only by default for new long-term material; classical for legacy backward-compatibility only.

## Consequences

### Positive

* No HNDL window. Every secret material Pulsar generates from Sprint 1.1 onward is safe against retroactive quantum decryption.
* Aligns with Cloudflare + Google Chrome + Apple iMessage + AWS KMS production deployments — Pulsar is in good company, not pioneering a risky novel construction.
* Hybrid construction inherits security guarantees of **both** primitives — strictly stronger than PQC-only or classical-only.
* HACL\* per ADR-0009 ships the PQC primitives formally verified — Pulsar's PQC posture is grounded in machine-verified primitives, not just NIST-finalist code.
* Banking + healthcare + government procurement (which increasingly evaluates PQC posture in 2026) sees the strongest available story.
* No future "PQC migration" project — the migration is "always already done" from day one.

### Negative

* Marginal compute cost: each KEM operation now runs both X25519 (negligible) and ML-KEM-768 (≈ 5-10× X25519 cost on x86-64). On HACL\*-optimised paths the absolute cost is sub-millisecond per operation; not user-visible for HTTP request latencies.
* Network bandwidth grows: ML-KEM-768 ciphertext is 1088 bytes vs X25519's 32 bytes; ML-DSA-65 signatures are 3293 bytes vs Ed25519's 64 bytes. For protocols where bandwidth dominates (e.g. mobile-network constrained clients), this is observable. Mitigation: PQC primitives apply only to long-term commitments (signatures, key establishment), not to per-message AEAD where bandwidth growth would matter.
* PQC primitives are 18 months old (FIPS 203/204 finalised August 2024). The hybrid posture mitigates the risk of a future cryptanalytic break in ML-KEM or ML-DSA — the classical side stays secure even if the PQC side falls.
* Compatibility with non-PQC peers requires runtime negotiation logic. Implementation cost in `pulsar-kernel::crypto::handshake` ≈ 200 LOC for negotiation + tests.

### Neutral

* Test surface grows: every cryptographic protocol now has classical-only + PQC-only + hybrid modes, each requiring tests. Mitigation: parametric tests via `proptest` cover all three modes from a single test definition.
* Performance benchmarks need to track three configurations rather than one; criterion supports this naturally via `criterion::Bench{Group}`.

## Alternatives considered

* **Classical-only Phase 1, hybrid PQC at Sprint 1.5** (v2.2 baseline).
  Rejected per the HNDL motivation: even if Pulsar is not in production at Sprint 1.5, test deployments + reference implementations + ecosystem partners may be, and any secret material they generate has 8+ year retention by regulatory mandate.
* **PQC-only without hybrid** (skip classical primitives entirely from Sprint 1.1).
  Rejected. NIST PQC standards are 18 months old; the conservative posture is hybrid for at least 5-10 years until the cryptanalytic literature on ML-KEM + ML-DSA matures. Hybrid is what every production deployment (Cloudflare, Google, Apple, AWS) uses for the same reason.
* **Defer PQC entirely to post-GA**.
  Rejected per the regulated-domain ambition. Banking + government procurement explicitly evaluates PQC posture in 2026; "PQC at v1.1" is a procurement non-starter for the target verticals.
* **Use NTRU or Classic McEliece instead of ML-KEM** (alternative PQC families).
  Rejected. NIST standardised ML-KEM as the primary recommendation in FIPS 203. NTRU is mature but not NIST-standardised; Classic McEliece is conservative + public-key-large (1 MB+) which is impractical for non-niche deployments. Pulsar follows NIST.

## Compliance mapping

* **NIST FIPS 203 (ML-KEM)** + **FIPS 204 (ML-DSA)** + **FIPS 205 (SLH-DSA)** — Pulsar's PQC posture conforms to all three NIST PQC standards (ML-KEM + ML-DSA used by default; SLH-DSA available as opt-in for mathematical-assumption diversity).
* **NIST SP 800-208** (Recommendation for Stateful Hash-Based Signature Schemes) — informational; Pulsar does not use stateful HBS schemes (XMSS, LMS) by default but `pulsar-kernel::crypto` has the hooks for opt-in if a downstream deployment requires them.
* **NIST FIPS 140-3 Level 2** (Decision 2.56 + Sprint 4.7) — the CMVP submission includes the PQC primitives + the hybrid construction.
* **EU CRA (Regulation (EU) 2024/2847) Annex I § 1(d)** (limit attack surfaces) — PQC posture limits the future-quantum attack surface from day one rather than adding it later.
* **NIS2 Art. 21(2)** (cybersecurity risk-management measures) — quantum-readiness is increasingly an explicit NIS2 evaluation criterion in 2026.
* **DORA Art. 9(2)** (preventive measures) — quantum-readiness is one of the canonical "preventive measures" for long-term confidentiality.
* **PSD2 RTS Art. 4** (security requirements for payment service providers) — payment-data confidentiality requirements span decades; HNDL mitigation is the relevant control.
* **eIDAS 2** (Regulation (EU) 910/2014 amended 2024) — qualified electronic signature schemes are increasingly expected to support PQC for archival validity beyond the classical-cryptography horizon.
* **HIPAA 45 CFR § 164.312(a)(2)(iv)** (encryption and decryption — addressable specification) — PHI retention spans decades; HNDL mitigation strengthens the encryption guarantee.
