# OWASP ASVS Level 2 — Pulsar control matrix

> Every ASVS L2 clause below maps to a Pulsar control, an explicit gap row, or an
> obligation that belongs to operations. **A status symbol is not evidence.** What an
> assessor can follow is the citation beside it: every ✅ row names the `file:line` the
> control is implemented at and the test that fails when it is removed, and every ⚠️ names
> which clauses of its section it does not reach and why. Read the Control column, not the
> tick — but here the tick can no longer say more than the column does.

## Status legend

- ✅ **Implemented**: a framework control exists and this row names it.
- ⚠️ **Partial**: control exists but has known coverage gaps, stated in the row.
- ❌ **Gap**: no framework-level control; downstream apps must add.
- 🔗 **External**: control belongs to operations or hosting, not the framework.

### How much a row is worth

A ✅ on this page means one thing and is allowed to mean nothing else: **the row names the
file and line the control is implemented at, and the test that fails when the control is
removed.** A row that could only name a module — `src/Auth/**`, `SessionConfig`, "MIME
sniffing" — is not evidence that a clause is satisfied; it is a place to start looking, and
twenty-eight rows were exactly that until this revision.

Each of the twenty-eight was reopened individually, against the code rather than against
the row. Sixteen turned out to have the evidence, and now cite it. Twelve did not, and say
so in the row instead of implying otherwise:

| Row     | Why it is no longer ✅                                                                    |
| ------- | ----------------------------------------------------------------------------------------- |
| `V1.2`  | 1.2.1 and 1.2.2 are deployment properties; no code here observes them                     |
| `V2.2`  | 2.2.1 stops at 2FA; 2.2.3 has no notification channel for the account holder              |
| `V2.5`  | only 2.5.7 ships; 2.5.1–2.5.6 need a password-reset flow the framework does not have      |
| `V4.3`  | the admin 2FA and role refusals have no behavioural test                                  |
| `V6.4`  | 6.4.2 asks for isolated key material; every operation is in-process (ADR-0006)            |
| `V8.1`  | 8.1.1 and 8.1.2 have no control over cached or temporary server-side copies               |
| `V8.2`  | anti-caching and `Clear-Site-Data` are per-handler opt-ins, not defaults                  |
| `V9.1`  | HSTS instructs a browser; 9.1.1–9.1.3 are the TLS terminator's settings                   |
| `V9.2`  | the default is proved, the connection is not — no test refuses a bad certificate          |
| `V12.1` | the body limiter ships and is tested, but nothing wires it and it trusts `Content-Length` |
| `V12.4` | 12.4.2 asks for content scanning; nothing in the tree scans an uploaded file              |
| `V13.1` | 13.1.5 is unmet — no caller rejects an unexpected or missing `Content-Type`               |

None of the twelve is a defect report. Each is what the row was already worth, written
down — the code did not change, only the claim about it. Two rows moved sideways rather
than down: `V12.2`'s size half belonged at `V12.1` and went there, leaving `V12.2` ✅ on
12.2.1 alone, which is the one clause it actually proves.

The discipline behind this is [ADR-0060](../adr/0060-a-check-never-observed-to-fail-is-indistinguishable-from-no-check.md):
a check never watched refusing is indistinguishable from no check, and a status written as
a literal is indistinguishable from a status nobody measured. `AsvsMatrixClaimsTest`
(`tests/Unit/Documentation/AsvsMatrixClaimsTest.php`) keeps this page to it: a ✅ row that
cites no `file:line`, or no test, or names a source file that is not in the tree, fails the
build.

### Data classification scheme (V6.1)

Levels are the cases of `Pulsar\Security\Compliance\DataClassification`
(`src/Security/Compliance/DataClassification.php`). The rule a level carries is a
storage rule: it names what a store must do before it may hold data at that level.

| Level          | Rule at rest                                                                              | Framework data at this level               | Control                                                                                             |
| -------------- | ----------------------------------------------------------------------------------------- | ------------------------------------------ | --------------------------------------------------------------------------------------------------- |
| `Public`       | none                                                                                      | rendered content, published config         | —                                                                                                   |
| `Internal`     | none beyond access control                                                                | request logs, metrics                      | access control; log scrubbing is V7.1                                                               |
| `Confidential` | never written in plaintext                                                                | TOTP seeds                                 | `Encryptor` under a derived subkey — `DatabaseTotpSecretStore`, subkey 4 / context `totpscrt`       |
| `Restricted`   | never written in plaintext, and under a KDF subkey of its own rather than the default one | cardholder PANs, operator secrets and DSNs | `TokenizationService`, subkey 7 / context `tokenize`; `SecretVault`, subkey 15 / context `secrets_` |

`MasterKey::deriveSubKey($id, $context)` separates on the **pair**: two callers sharing
both an id and a context derive identical bytes, and differing in either is enough to
separate them. That is why the `Restricted` row asks for a domain of its own rather than
the default encryption key.

`src/Security/Crypto/SubKeyId.php` is the registry the enum's own docblock asks callers to
import, and **none of the three subsystems in the table above is in it**. Their ids are
literals at the call site, and each collides with an id the enum has allocated to something
else:

| Subsystem                 | Derives            | Call site                                                                                | `SubKeyId` says that id belongs to |
| ------------------------- | ------------------ | ---------------------------------------------------------------------------------------- | ---------------------------------- |
| `DatabaseTotpSecretStore` | `(4, 'totpscrt')`  | `src/Core/Wiring/AuthWiring.php:325`                                                     | `Csrf = 4`                         |
| `TokenizationService`     | `(7, 'tokenize')`  | `src/Security/Crypto/TokenizationService.php:39` (wired at `SecurityWiring.php:239-243`) | `Studio = 7`                       |
| `SecretVault`             | `(15, 'secrets_')` | `src/Security/Vault/SecretVault.php:44` (wired at `SecurityWiring.php:399`)              | `ComplianceDerivationProbe = 15`   |

The keys these three derive are still distinct from every other key in the framework,
because no other caller uses the same context string — the separation the KDF actually
provides holds. What does not hold is the registry: `SubKeyId`'s docblock states that "each
subsystem [...] must use a unique `$id` integer", and these three, along with the session
fingerprint key (`4, 'sess_fp_'`), the Studio archive and chain MACs (`4`/`5`), the CMS key
manager (`10`–`15`) and anti-spam signing (`16`/`17`), do not. A reader who opens
`SubKeyId.php` to find out which subsystem owns id 4 gets the wrong answer for three of the
four that use it. Treat the enum as a partial registry and the call sites as authoritative
until the two are reconciled; an earlier revision of this page said the ids "are allocated
in `SubKeyId.php`", which sent a reader to a file that does not contain them.

The scheme binds nothing at runtime. `DataClassification` reaches API field policies
(`src/Api/Resource/FieldPolicy.php`, `RedactionRule.php`), break-glass access
(`src/Security/JustifiedAccess/**`) and compliance snapshots
(`src/Security/Compliance/Snapshot/**`) — every one of them a read path. No storage
class consults it, so the table above is upheld by review.

## Open gaps (active work)

- **V2.3 / V2.9** — WebAuthn conformance vector suites (ADR-0032). V2.7 no longer belongs in this bullet: out-of-band verification has no control here at all, and no work on one is under way.
- **V10.2 / V10.3** — Plugin signature. The V10.3 half is narrower than it was: the deploy check verifies the manifest and its signature rather than the `integrity.enabled` flag, and added files now fail verification. What remains is the key model — `ManifestSigner` HMACs with a subkey of the master key that sits on the host being protected, so an attacker who can rewrite files can re-run `integrity:build` and re-sign. Closing it means signing the manifest with an offline Ed25519 key, which `ArtifactSigner` already does for release artifacts.
- **V14.2** — the merge SLA is policy, not machinery: no workflow reads Dependabot PR labels or measures time-to-merge (`docs/dependabot-sla.md`). Separately, `SbomGenerator` enumerates the root lockfile only, so bundled-extension dependencies are now audited but still absent from the SBOM.
- **V8.3** — the token vault has no durable default. `SecurityWiring.php:204-207` falls back to `InMemoryTokenStore` whenever the application has bound no `TokenStoreInterface`, so every token a worker issues is orphaned when it recycles and the PAN behind it becomes unrecoverable. `DatabaseTokenStore` is written and tested (`tests/Unit/Security/Crypto/DatabaseTokenStoreTest.php`) but no configuration key selects it, so nothing but hand-wiring reaches it. The earlier claim here — "PCI tokenization is implemented (BLAKE2b keyed); the gap is downstream documentation, not framework code" — was wrong on both halves: nothing on the tokenization path hashes anything, keyed or otherwise, and the framework code had the gap.
- **V11.1** — three items behind the disclaimer that replaced this section's single row. (1) 11.1.8 records but does not deliver: the default binding is now `FileIncidentReporter`, so the register is durable, but no mail, webhook or pager channel ships and nothing notifies a human. (2) 11.1.4 — `AuthenticationRateLimitMiddleware`, the separate-budget limiter for login, password reset and 2FA verify, is constructed nowhere in the framework; it exists only as the `auth-rate-limit` entry in `MiddlewareAliasConfig`, which the kernel never applies, so reaching it needs a wiring change to register the alias. (3) 11.1.1 — no separation of duties exists: `RoleGuard` authorizes against roles frozen into the instance context at `start()` rather than against the acting principal, so `ApprovalWorkflow` permits self-approval and `RoleGuardTest.php:39` pins that as expected. Each needs a file outside this row (`SecurityWiring`, `AuthWiring`, `src/Workflow/Guard/**`).
- **V12.3** — the form extension's upload directory is outside the document-root guard. `WritablePathGuard` is `#[Api]`, but `tools/php/deptrac.yaml` grants no extension layer a dependency on `Pulsar\Filesystem`, so `UploadConfig` cannot reach it; closing this needs `Filesystem` added to the extension layers' allowed dependencies before the check can be written.
- **V13.2** — the REST clauses themselves are unimplemented, not merely uncited: nothing verifies a request's `Content-Type` (13.2.5 — `ResponseStatus::UnsupportedMediaType` has no caller anywhere), nothing validates a JSON body against a schema (13.2.2), and no middleware group is attached to the auth extension's routes, so a cookie-authenticated REST call has no CSRF or origin control (13.2.3). Separately, the seven `/webauthn/*` ceremony endpoints have no framework-supplied HTTP layer, which is now a stated decision rather than an omission: `AuthExtension::boot()` declines to register them because each needs session-bound challenge state and an ownership check the extension does not own, and `docs/webauthn.md` says so and hands the application the ceremony surface through `WebAuthnServerInterface`. That doc and `docs/oauth2-oidc.md` described the pre-merge `pulsar/webauthn` and `pulsar/oauth2` packages; both are rewritten against `pulsar/auth`, so what remains under this clause is the three unimplemented REST items above, not the naming.

## How this page is held to what it says

This matrix is hand-maintained markdown, and hand-maintained pages rot. Two things bound
the rot rather than promising it away:

- `tests/Unit/Documentation/AsvsMatrixClaimsTest.php` reads this file on every `composer
test` run. A ✅ row that cites no `file:line`, a ✅ row that names no test, a row citing a
  source or test path that is not in the tree, or a downgrade table naming a row that is
  back to ✅ — each fails the build. It grades citations, not prose: it cannot tell whether
  a control is correct, only whether the row still points at something real.
- **For what a running deployment achieves, run `pulsar compliance:report`.** This page
  describes the framework and cannot observe your deployment;
  [ADR-0045](../adr/0045-a-control-status-is-observed-not-written.md) is why the compliance
  system refuses to let a status be written down at all. Note that the report writes — see
  [Compliance](../compliance.md) before running it against production.

A machine-readable YAML form remains unwritten, and this page does not promise one.
