# OAuth2/OIDC + WebAuthn Threat Model

Security red team analysis of the Pulsar Framework OAuth2/OIDC and WebAuthn extensions.

Methodology: STRIDE-per-element threat modeling with code-level verification against each attack vector.

## Attack Vector Analysis

### 1. Token Theft and Replay Attacks

| Field          | Value                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| -------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Threat         | An attacker intercepts a bearer access token and replays it to gain unauthorized access                                                                                                                                                                                                                                                                                                                                                                                            |
| STRIDE         | Spoofing, Information Disclosure                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| Risk Level     | Medium                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| Mitigation     | Access tokens are opaque random values (64 hex chars via `random_bytes(32)`). Tokens are stored hashed (SHA-256) in the repository (`InMemoryAccessTokenRepository:38-39`). Token expiry is enforced at introspection time (`AccessToken::isActive()` checks `!revoked && !isExpired()`). Revocation endpoint allows immediate invalidation (`LeagueAuthorizationServer:403-417`). Cache-Control: no-store headers prevent caching (`LeagueAuthorizationServer:191-192, 223-225`). |
| Status         | Mitigated                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| Recommendation | Consider adding DPoP (RFC 9449) token binding for sender-constrained access tokens in a future release. Token lifetime of 3600s is reasonable but configurable TTL would allow tightening for high-security deployments.                                                                                                                                                                                                                                                           |

### 2. Authorization Code Interception

| Field          | Value                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| -------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Threat         | An attacker intercepts the authorization code from the redirect URI and exchanges it for tokens                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| STRIDE         | Spoofing, Tampering                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| Risk Level     | Low (mitigated by mandatory PKCE)                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| Mitigation     | PKCE is mandatory -- `code_challenge` is a required parameter (`LeagueAuthorizationServer:121`). Only S256 method is accepted; plain is rejected (`LeagueAuthorizationServer:130-132`, `AuthorizationCodeGrant:72-74`). PKCE verification uses timing-safe `hash_equals()` (`AuthorizationCodeGrant:208`). Authorization codes are one-time use via atomic consumption (`InMemoryAuthorizationCodeRepository:40-63`). Codes have a 10-minute TTL (`AuthorizationCodeGrant:41`). Redirect URI is validated by strict exact match (`OAuthClient::hasRedirectUri`, `AuthorizationCodeGrant:133`). |
| Status         | Mitigated                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| Recommendation | None. PKCE S256-only with one-time use and short TTL is best practice per RFC 7636 and OAuth 2.1 draft.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |

### 3. Refresh Token Rotation Bypass

| Field          | Value                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Threat         | An attacker reuses a previously rotated-out refresh token to obtain new tokens, bypassing rotation                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| STRIDE         | Spoofing, Elevation of Privilege                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| Risk Level     | Low (mitigated by replay detection)                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| Mitigation     | Refresh tokens are one-time use with rotation: `consume()` marks the token as consumed before returning it (`InMemoryRefreshTokenRepository:78`). Replay detection: if a consumed token is reused, `consume()` revokes the entire token family via `revokeFamily()` (`InMemoryRefreshTokenRepository:66-69`). The `wasReplayDetected()` flag triggers a `SecurityEvent` audit log (`RefreshTokenGrant:69-79`). Family-based revocation ensures all descendant tokens become invalid (`InMemoryRefreshTokenRepository:126-132`). Tokens are stored hashed, preventing direct database extraction. |
| Status         | Mitigated                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| Recommendation | None. Token family revocation on replay is the gold standard per OAuth Security BCP.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |

### 4. Client Impersonation / Confused Deputy

| Field          | Value                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Threat         | Tokens issued to Client A are presented by Client B to access resources, or a malicious client impersonates a legitimate client                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| STRIDE         | Spoofing, Elevation of Privilege                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| Risk Level     | Low                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| Mitigation     | Every token carries an immutable `clientId` binding (typed in `AccessToken`, `RefreshToken`, `AuthorizationCode`). The authorization code exchange verifies client binding: `$authCode->clientId !== $client->id` (`AuthorizationCodeGrant:128-129`). Refresh token exchange verifies client binding: `$oldRefreshToken->clientId !== $client->id` (`RefreshTokenGrant:85-87`). Revocation only permits the issuing client to revoke its own tokens (`LeagueAuthorizationServer:390, 412`). Client authentication is required for token requests via Basic auth or body params (`LeagueAuthorizationServer:305-372`). Client credentials grant restricted to confidential clients only (`ClientCredentialsGrant:49-52`). |
| Status         | Mitigated                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| Recommendation | None. Client binding is enforced at every token lifecycle point.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |

### 5. Open Redirect via redirect_uri

| Field          | Value                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Threat         | An attacker provides a malicious redirect URI to steal authorization codes or tokens via open redirect                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| STRIDE         | Tampering, Information Disclosure                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| Risk Level     | Low                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| Mitigation     | Redirect URI validation uses strict exact match with no wildcards (`OAuthClient::hasRedirectUri` at `OAuthClient:38-41` uses `in_array($uri, $this->redirectUris, true)`). Validation is performed both at authorization request time (`LeagueAuthorizationServer:145-147`) and at authorization code creation time (`AuthorizationCodeGrant:76-78`). Error redirects also validate the URI against registered URIs before redirecting (`LeagueAuthorizationServer:444-446`). No pattern matching, no subdomain matching, no path normalization. |
| Status         | Mitigated                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| Recommendation | None. Strict exact match is the strongest redirect URI validation policy.                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |

### 6. CSRF in Authorization Flow

| Field          | Value                                                                                                                                                                                                                                                                                                                                                                       |
| -------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Threat         | An attacker initiates an authorization flow on behalf of a victim, causing the victim to unknowingly authorize the attacker's account                                                                                                                                                                                                                                       |
| STRIDE         | Tampering                                                                                                                                                                                                                                                                                                                                                                   |
| Risk Level     | Low                                                                                                                                                                                                                                                                                                                                                                         |
| Mitigation     | The `state` parameter is passed through and returned in the redirect (`LeagueAuthorizationServer:183-185`). PKCE serves as an additional CSRF protection since only the party that generated the code_verifier can exchange the code. However, the authorization server does not itself validate the `state` parameter -- this is the client's responsibility per RFC 6749. |
| Status         | Mitigated                                                                                                                                                                                                                                                                                                                                                                   |
| Recommendation | The server-side implementation correctly passes `state` through. PKCE provides server-side CSRF protection. Client-side state validation is the client's responsibility per specification.                                                                                                                                                                                  |

### 7. WebAuthn Relay/Replay Attacks

| Field          | Value                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| -------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Threat         | An attacker intercepts a WebAuthn challenge-response and replays it, or relays it from another origin                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| STRIDE         | Spoofing, Tampering                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| Risk Level     | Low                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| Mitigation     | Challenges are cryptographically random 32 bytes (`RegistrationCeremony:48`, `AuthenticationCeremony:39`). Challenge verification uses timing-safe `hash_equals()` (`RegistrationCeremony:196`, `AuthenticationCeremony:240`). Origin is verified against the configured origin (`RegistrationCeremony:203`, `AuthenticationCeremony:247`). RP ID hash in authenticator data is verified against the configured RP ID (`RegistrationCeremony:218-222`, `AuthenticationCeremony:261-265`). Signature counter is checked for monotonic increase to detect cloned authenticators (`AuthenticationCeremony:137-153`). |
| Status         | Mitigated                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| Recommendation | Challenges should be stored server-side with a TTL and consumed on verification to prevent replay within the TTL window. The current implementation relies on the caller to manage challenge state. Consider adding `tokenBinding` channel binding when browser support matures.                                                                                                                                                                                                                                                                                                                                  |

### 8. Attestation Forgery

| Field          | Value                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| -------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Threat         | An attacker submits a forged attestation statement to register a credential with fabricated trust properties                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| STRIDE         | Tampering, Spoofing                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| Risk Level     | Medium                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| Mitigation     | Format policy is enforced via an allowlist (`AttestationVerifier:28-31, 38-39`). Disallowed formats throw `WebAuthnException::disallowedFormat()`. For 'none' attestation, the `attStmt` must be empty (`AttestationVerifier:75-77`). For 'packed' attestation with x5c, the signature is verified against the certificate public key using `openssl_verify()` (`AttestationVerifier:143-147`). For packed self-attestation, the signature is verified against the credential public key extracted from authData (`AttestationVerifier:180`). COSE algorithm mapping covers ES256, ES384, ES512, RS256, RS384, RS512, PS256, PS384, PS512 (`AttestationVerifier:362-372`). |
| Status         | Partially Mitigated                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| Recommendation | The packed full attestation path does not perform certificate chain validation against a trust store (e.g., FIDO MDS). An attacker could self-sign a certificate for packed/full attestation. For regulated deployments, integrate FIDO Metadata Service (MDS) validation to verify attestation certificate chains against known authenticator vendors.                                                                                                                                                                                                                                                                                                                    |

### 9. ID Token Substitution / Audience Confusion

| Field          | Value                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| -------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Threat         | An ID token issued for Client A is presented to Client B, which accepts it as valid, causing audience confusion                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| STRIDE         | Spoofing, Elevation of Privilege                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| Risk Level     | Low                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| Mitigation     | The `aud` claim is set to the specific `clientId` at issuance (`IdTokenBuilder:54`). The `iss` claim is set to the configured issuer (`IdTokenBuilder:52`). The `sub` claim is resolved via `UserClaimsProviderInterface::getSubjectIdentifier()` which supports pairwise subject identifiers per client (`IdTokenBuilder:53`, `UserClaimsProviderInterface:43`). The nonce from the authorization request is included when provided (`IdTokenBuilder:59-61`). JWT signatures use Keyring-managed keys with `hash_equals()` for verification (`JwtSigner:91`). |
| Status         | Mitigated                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| Recommendation | For production deployments, replace HMAC-SHA256 (HS256) with asymmetric signing (RS256 or ES256) so that clients can verify tokens without possessing the signing key. The current HS256 implementation requires shared secrets and is unsuitable for public clients.                                                                                                                                                                                                                                                                                          |

### 10. Token Binding Bypass (Refresh Token)

| Field          | Value                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Threat         | Refresh tokens are used outside their intended context (different client, different subject, different session)                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| STRIDE         | Elevation of Privilege, Spoofing                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| Risk Level     | Low                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| Mitigation     | Refresh tokens carry immutable bindings to `clientId`, `subjectId`, `sessionId`, and `familyId` (`RefreshToken:25-29`). Client binding is checked at refresh time (`RefreshTokenGrant:85-87`). Subject binding is preserved through rotation -- new refresh token inherits `subjectId` (`RefreshTokenGrant:120`). Session binding is preserved through rotation (`RefreshTokenGrant:121`). Family binding is preserved for cascade revocation (`RefreshTokenGrant:122`). Scope narrowing is permitted but scope expansion is rejected (`RefreshTokenGrant:94-99`). |
| Status         | Mitigated                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| Recommendation | None. The four-way binding (client + subject + session + family) provides comprehensive token binding.                                                                                                                                                                                                                                                                                                                                                                                                                                                             |

## Open Findings

### F-1: No certificate chain validation for packed attestation (Medium)

The `AttestationVerifier::verifyPackedFull()` method verifies the attestation signature against the certificate but does not validate the certificate chain against a trust anchor (FIDO MDS). An attacker could self-sign a certificate and produce a valid packed/full attestation that passes verification. For regulated deployments requiring authenticator provenance, integrate FIDO Metadata Service validation.

**File**: `extensions/webauthn/src/Adapter/AttestationVerifier.php:126-155`

### F-2: HMAC-SHA256 signing for ID tokens (Low)

The `JwtSigner` uses HMAC-SHA256 (HS256) with symmetric keys from the Keyring. This requires sharing the signing key with any party that needs to verify ID tokens, which is unsuitable for public clients. Asymmetric signing (RS256/ES256) would allow token verification without key sharing.

**File**: `extensions/oauth2/src/Oidc/JwtSigner.php:49-53`

### F-3: Challenge state management delegated to caller (Low)

The WebAuthn ceremonies generate challenges and return them to the caller, but challenge consumption (preventing reuse) is not enforced within the ceremony itself. The caller must implement server-side challenge storage and TTL enforcement. A built-in challenge store with automatic expiry would reduce integration error risk.

**Files**: `extensions/webauthn/src/Ceremony/RegistrationCeremony.php:108`, `extensions/webauthn/src/Ceremony/AuthenticationCeremony.php:93`
