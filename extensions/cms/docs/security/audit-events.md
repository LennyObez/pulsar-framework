# CMS Audit Events Reference

This document provides a complete taxonomy of all audit events generated by Pulsar CMS. Each event is recorded through the framework's `AuditLoggerInterface` with a structured format suitable for compliance, forensics, and monitoring.

## Audit Record Format

Every audit record contains:

| Field      | Type        | Description                                               |
| ---------- | ----------- | --------------------------------------------------------- |
| Event Type | enum        | Category of the event                                     |
| Outcome    | enum        | Result of the action                                      |
| Actor ID   | string/null | User ID who performed the action (null for system events) |
| Action     | string      | Machine-readable action identifier                        |
| Subject    | string      | The affected resource identifier                          |
| Evidence   | map         | Additional context fields                                 |
| Timestamp  | datetime    | When the event occurred (auto-generated)                  |

### Event Types

| Type                  | Description                                                    |
| --------------------- | -------------------------------------------------------------- |
| `SecurityEvent`       | Security-related events (2FA, sanitizer bypass, bot detection) |
| `Authentication`      | Login, verification, and authentication events                 |
| `DataModification`    | Content, comment, and data change events                       |
| `ConfigurationChange` | Settings and configuration changes                             |

### Outcome Values

| Outcome   | Description                                              |
| --------- | -------------------------------------------------------- |
| `Success` | The action completed successfully                        |
| `Failure` | The action failed (e.g., invalid code, validation error) |
| `Denied`  | The action was blocked by a security control             |

## Content Lifecycle Events (Event Sourcing)

When `event_sourcing` is enabled, the `ContentEventService` records immutable events for all content mutations. These are stored in the event store table, separate from audit logs.

| Event              | Description                                        |
| ------------------ | -------------------------------------------------- |
| `ContentCreated`   | New content item created                           |
| `ContentUpdated`   | Content item modified                              |
| `ContentPublished` | Content transitions to Published status            |
| `ContentArchived`  | Content transitions to Archived status             |
| `ContentRestored`  | Content restored from Archived to Draft            |
| `ContentDeleted`   | Content soft-deleted                               |
| `RevisionCreated`  | New revision created for a content item            |
| `SlugChanged`      | Content slug modified (triggers redirect creation) |

Each event sourcing entry includes:

| Field           | Description                                |
| --------------- | ------------------------------------------ |
| Event ID        | Unique event identifier                    |
| Content ID      | The affected content item                  |
| Event Type      | Event classification                       |
| Actor ID        | User who performed the action              |
| Payload         | Serialized event data                      |
| Timestamp       | Event timestamp                            |
| Sequence Number | Monotonic ordering within a content stream |

## Retention Policies

### Audit Logs

Audit log retention should be configured based on regulatory requirements:

| Regulation         | Minimum Retention                          |
| ------------------ | ------------------------------------------ |
| GDPR               | Duration of processing + reasonable period |
| SOX (financial)    | 7 years                                    |
| HIPAA (healthcare) | 6 years                                    |
| PCI DSS            | 1 year (3 months immediately accessible)   |

### Event Store

Content event store entries are immutable and should be retained for the lifetime of the content item. They serve as the authoritative record of all content mutations.

### Recommendations

1. Configure log rotation to archive old audit entries
2. Store archived logs in tamper-evident storage
3. Set up alerts for `SecurityEvent` entries with `Failure` or `Denied` outcomes
4. Monitor `cms.2fa.verify_failed` frequency for brute-force detection
5. Review `cms.comment.honeypot_triggered` to assess bot activity levels
